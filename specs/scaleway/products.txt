# Produits Scaleway suivis par le générateur, un par ligne.
#
#   <slug-portail> [<nom-produit>] <version>
#
# Le slug est celui de l'URL du portail developers, et il ne coïncide pas
# toujours avec le nom du produit dans les SDK. Mesuré sur le portail :
# baremetal s'y appelle elastic-metal, k8s s'y appelle kubernetes, lb s'y
# appelle load-balancer/zoned. Un produit ajouté ici se vérifie sur sa page,
# il ne se devine pas depuis le SDK.
#
# Instance a servi de premier produit : la chaîne complète a fonctionné sur lui
# avant qu'un second n'arrive. `lb` est ce second, et il est choisi pour une
# raison mesurable plutôt que par appétence : la stack d'exemple déploie déjà un
# load balancer, donc ses modules sont exercés contre le cloud réel dès le
# premier jour, sans écrire de nouvelle plateforme. C'est le produit dont la
# preuve coûte le moins cher.

instance v1
load-balancer/zoned lb v1

# Suivis sans être générés. `suivi` en fin de ligne range le contrat sous
# `suivis/`, où le générateur ne le voit pas : il n'y a ni module, ni rapport,
# ni golden pour ces produits.
#
# **Pourquoi les versionner quand même.** L'inventaire dynamique appelle six
# APIs, et deux seulement avaient un contrat. `ipam.list_i_ps_all`,
# `vpc.list_private_networks_all` et `vpc.list_vp_cs_all` portent la jointure
# qui donne son adresse privée à chaque machine, et cette jointure lit ses
# champs par `getattr(..., None)` : un champ renommé en amont rend `None` en
# silence, et l'inventaire un parc muet. C'était la dérive la moins mesurée du
# dépôt, sur la fonction la plus mise en avant.
#
# **Pourquoi ne pas les générer.** Élargir la génération à un produit que la
# collection ne sert pas ajouterait des UNKNOWN permanents, et le mode strict
# sortirait en 2 pour du travail que personne n'a demandé.
ipam v1 suivi
vpc v2 suivi
elastic-metal baremetal v1 suivi
apple-silicon applesilicon v1alpha1 suivi
